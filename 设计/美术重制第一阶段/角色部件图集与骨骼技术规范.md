## 1. 核对范围与术语

核对对象为当前独立工作区 `源代码/HeroPoseRig.cs`、`RasterActorRenderer.cs`、`RasterAtlas.cs`，以及 `AdventureArt.cs` 的载入、主角绘制、尺寸缩放、素材验证分支；补充核对 `AdventureController.cs` 的主角尺寸、`KnightPet.cs` 的透明命中与 `验证工具/HeadNeckPreview.cs`、`RigContactValidation.cs` 的现有验收假设。

- **图集 cell**：一格原始绘画画布。新候选规范为 512×512 px；不等于程序最终取用的有效图像边界。
- **rects 区域**：程序按行号读取的源图矩形，使用图集像素坐标，行号即索引；它可以覆盖完整 cell，也可以是旧图的不规则区域。
- **alpha bounds / 裁切边界**：程序在 rects 区域内扫描 alpha 后形成的有效边界，含少量扩边。当前部件绘制主要使用这个边界的缓存图。
- **近侧 / 远侧**：相对于观察者的前后层级，不是屏幕左右。所有原画统一面向右；向左由程序整体镜像。
- **基准坐标**：程序的 220×220 骨架坐标，原点左上，x 向右，y 向下。

本文的像素均指资源或渲染输出的实际像素；Windows 显示缩放和截图软件缩放应另行记录，不得混作资源尺寸。

## 2. 当前运行契约：已有代码实际如何工作

### 2.1 文件、索引与启动条件

当前六套主题为 `OTHER`、`CN`、`JP`、`US`、`TW`、`HK`。主角图集按 `rig-{主题}.png` 加载，构造参数为 4 列×3 行，共 12 格。`HasRig` 检查 0–10 号的 11 个动画部件；正式非空素材目录的 `AdventureRenderer` 构造还会调用 `Validate`，要求 0–11 号全部有效，因此第 11 号完整角色参考图也必须交付。

`RasterAtlas` 单独使用时找不到 `.rects` 会尝试平均分格，但启动素材验证明确要求每张图集存在同名 `.rects`。所以可运行的正式素材包必须把 PNG 与 `.rects` 作为一对版本化文件交付；“PNG 能打开”或“平均分格能读到”不是启动通过的证据。损坏 rects、越界或数量错误会令该图集加载失败；上层将报告素材不完整。

| 索引（从 0 开始） | 当前用途 | 当前绘制与连接方式 |
|---|---|---|
| 0 | 头部 | 单张刚性头部，围绕头颈连接点旋转；不把脸分成多个活动块 |
| 1 | 躯干、衣领、腰裙主体 | 固定目标矩形 `(85,103,55,53)`，随身体父变换 |
| 2 | 近侧上臂 | 肩→肘，位于躯干前 |
| 3 | 近侧前臂与握持手 | 肘→主握点，位于武器前 |
| 4 | 远侧上臂 | 肩→肘，先于躯干绘制 |
| 5 | 远侧前臂与握持手 | 肘→副握点，位于武器前 |
| 6 | 近侧大腿 | 胯→膝，位于腰裙前 |
| 7 | 近侧小腿与靴 | 膝→踝；靴子从同一缓存图中重叠采样，另作脚掌转动 |
| 8 | 远侧大腿 | 胯→膝，位于躯干后 |
| 9 | 远侧小腿与靴 | 与 7 相同的组合结构 |

当前主角由后到前的主要层序是：披风、远上臂、远腿、颈补片/躯干、近腿、近上臂、头、武器、远前臂手、近前臂手。前臂和握持手在武器前方；制作时应据此检查袖口、手掌和衣领的遮挡。

当前实际源图并非统一的方格图：已核对 `rig-OTHER`、`rig-CN`、`rig-JP` 为 **1254×1254**，`rig-US`、`rig-TW`、`rig-HK` 为 **1448×1086**；它们依赖现有 `.rects` 指定的不规则矩形。1254 方图不能被描述成“已经符合 4×3 等大方格规范”，也不能先均分再宣称旧部件无损。旧文件只作兼容基线，不作为新资源合规样板。

### 2.2 骨架、尺寸与左右方向

`HeroPoseRig` 连续计算关节，不读取 12 帧动作序列。12 格代表部件，不代表动画帧。跑步周期可以采样 60 帧或更多帧用于预览，运行本身不是固定帧表。

当前关键目标点与长度如下，单位均为 220×220 基准坐标：

| 项目 | 当前值或行为 |
|---|---|
| 身体旋转中心 | `(110,143)`；叠加 bob、lean 与攻击前冲 |
| 近、远肩 | `(96,112)`、`(126,111)`，随身体父变换 |
| 近、远胯 | `BodyPoint(104,146)`、`BodyPoint(120,144)` |
| 手臂长度 | 近侧上/前臂 24/23；远侧上/前臂 22/23 |
| 腿部长度 | 大腿 23，小腿 25；膝盖朝前，长度由两段逆运动学约束 |
| 鞋底基准 | 近侧地面 y=191，远侧 y=188；踝点比鞋底高 10 |
| 支撑/抬脚 | 支撑占周期 0.52，支撑脚底水平；抬脚最高约 25，脚部独立转动 |
| 头部绘制 | 高 91，宽 `min(118, 91 × 裁切宽/裁切高)`，按主题头颈点和头部相对锚点对齐 |
| 左向 | 以基准宽度 220 作 `x' = 220 - x` 的整体变换；不加载另一套左向部件 |

主角控制器默认窗口为 **220×240**，其缩放形式是 `(int)(220×displayScale)`、`(int)(240×displayScale)`；渲染器内部主角仍按 220×220 坐标绘制，最终按 `sx=W/220`、`sy=H/220` 缩放。因此默认输出纵向为 `240/220≈1.0909`，并非等比缩放。176×192 与 264×288 保留相同的纵横比例。`RecommendedSize("Hero")` 和多项既有预览/自测默认仍为 220×220，不能用它们代替实际 220×240 验收。

当前必须兼容的动作路径包括 run/running、idle/rest/pant/panting、attack、dying/death、grave/tombstone/dead、revive/reviving。死亡后段切换墓碑与灵魂；复活带遮罩和土层。新角色部件不能保证改变这些动作的美术逻辑，尤其不能只画站姿后声称全部动作已适配。

### 2.3 当前锚点并非外部数据

当前没有加载角色锚点 JSON 的逻辑。现有自动锚点与主题分支是兼容行为：

1. 上/前臂及大腿的 `Start` 在**已裁切、已缩小的缓存图**高度约 14% 处，`End` 在约 85% 处；前臂 End 为 84%。x 为该水平带的 alpha 加权中心。
2. 小腿+靴 Start 在缓存高度 12%，踝点在 68%；`rig-TW.png` 特判为 59%。足部采样从踝比例减 8% 的高度开始，与小腿采样重叠。鞋底从底部 20% 向上寻找 alpha>80 的最后有效行。
3. 头部 `HeadSourceAnchor` 是**裁切图目标尺寸中的归一化比例**，不是原始 cell 坐标：OTHER `(0.69,0.89)`、CN `(0.64,0.92)`、JP `(0.64,0.94)`、US `(0.66,0.87)`、TW `(0.66,0.76)`、HK `(0.66,0.94)`。
4. 躯干颈点为基准坐标：OTHER/JP `(117,110)`、CN `(115,111)`、US `(117,111)`、TW `(118,110)`、HK `(117,114)`。头发、飘带、围巾最下端不能冒充下颌连接点。
5. 程序还在头和衣领后绘制椭圆颈部补片，外沿 12×13、内填 9×10。当前肤色按主题硬编码：OTHER 蓝灰、TW 绿色、其余暖肤色。新肤色或新领型若直接替图，可能露出旧补片；是否继续使用、换色或改为部件，须列入后续接入工作。

因此，新资产若暂不改程序，需要保持“垂直展开、上端起点、下端终点”的部件结构、现有比例和轮廓重心，并逐个实测自动锚点。极长飘带、横展手臂、偏心装饰、很长的脚尖都可能改变自动检测结果。**不能承诺任意体型、手脚比例或服饰只换 PNG 即可工作。**

### 2.4 当前武器与双握点

武器位于独立的 `weapons-v5.png/.rects`，不占主角的 12 格。主手取近侧前臂末端，副手位置由武器两个握点差经武器角度旋转后得到，再反算远侧肘。握点表为武器裁切图的目标矩形比例：

| 武器 ID | 目标宽 | 主握点（u,v） | 副握点（u,v） | 双手 |
|---|---:|---|---|---|
| spear | 137 | 0.34,0.58 | 0.54,0.43 | 是 |
| greatsword | 99 | 0.12,0.78 | 0.25,0.60 | 是 |
| wave | 94 | 0.17,0.82 | 0.38,0.62 | 是 |
| laser | 87 | 0.26,0.78 | 0.55,0.52 | 是 |
| boomerang | 66 | 0.72,0.52 | 0.72,0.52 | 否 |
| blackhole | 87 | 0.15,0.82 | 0.37,0.64 | 是 |
| automaton | 85 | 0.26,0.78 | 0.58,0.52 | 是 |

目标高按裁切纵横比计算，长枪上限 78，其余上限 83。所有手掌需要有可辨认的握柄中心；不能将手指尖或宽大袖口的边缘当作握点。新武器外形、柄长或握持方式变化，需要重标双握点并验证手臂可达性。

### 2.5 alpha、有效像素、缓存与命中

| 环节 | 当前规则 | 对新素材的约束 |
|---|---|---|
| 图集背景透明率 | alpha<16 计为透明；整体比例须 >0.15 且 <0.98 | 是启动粗检，不保证无白边、无杂点或安全边合格 |
| 有效墨迹与裁切 | 只将 alpha>24 计入；边界按此墨迹向外约 2 px，并限制在源矩形内 | 低 alpha 光晕可能被裁断；不能靠透明薄雾扩大有效边界 |
| 有效 cell | 有效墨迹至少 64 像素；验证另要求超过源矩形面积的 1.5% | 新512格至少须有3933个 alpha>24 像素；窄部件不能无限缩小在格中 |
| 自动横带中心 | alpha<40 不参与加权，等于40可参与 | 淡色不等于低alpha；关键连接主体应保持实心 |
| 鞋底识别 | alpha>80 才可成为鞋底 | 靴底应有稳定实色，不靠发光投影支撑 |
| 透明窗命中 | 输出帧 alpha<20 穿透，alpha≥20 可命中；PassThrough 开启时整体穿透 | 散落低透明装饰会改变鼠标命中范围，需检查 |
| 输出帧边缘既有测试 | 最外一行/列 alpha>12 判为越界 | 只查最外边并不足以证明有安全空隙 |

缓存保留 PNG 原文件，但运行图会先裁切再做一次高质量双三次预滤波，绘制时主要用双线性采样。rig 部件的缓存最长边上限：头 192 px、躯干 128 px、披风 160 px、参考图 288 px，其余肢体 96 px；源部件更小时不放大。**512 源图不代表 512 像素细节都能进入最终画面**。部件表面纹理、细线和脸部特征必须经过上述缓存及实际输出缩小检查。

## 3. 新资产规范：已确认约束与候选技术规格

### 3.1 产品已确认约束与Codex主候选规格

产品已确认的视觉范围是国漫仙侠·精致微缩风、高质量2.5D、约2.8—3头身；衣装与随身物件以布料、玉、金属形成可辨识的材质层次。三阶段是同一修士的成长，不是三个身份无关的人物：

| 阶段 | 已确认气质 | 适配时需保持 |
|---|---|---|
| 凡人 | 朴素 | 先从三张候选中确认脸、发型和衣装，选定后与后两阶段保持一致身份及约2.8—3头身框架 |
| 炼气 | 清逸 | 同一人物的连续辨识特征；不能自行改成另一张脸或另一种性别表达 |
| 筑基 | 沉稳 | 以确认稿呈现成长后的气质与材质层次，不擅自追加大型配饰或确定配色 |

产品已确认运行显示目标220×240、后续4列×3行12格、11独立部件加1完整参考。**2048×1536 px源图与每格512×512 px为Codex提出的主候选规格，尚非产品确认项**；RGBA真alpha、索引从左到右/从上到下用于满足当前载入与拆件要求。1536×1152（每格384）只作为后续另提的备选，本文件的候选坐标表统一按512格编写，避免混用。人物身份与三阶段确认后，再结合实际文件评估源图分辨率与本规格是否匹配；本轮独立原画不等于拆件母版。

2.8—3头身是新造型约束，不能表述成当前旧骨架与图像已经达到该比例。收到设计稿后需对照现有头高91、固定肩胯点与腿长，判断是否能在保持已确认人物比例的情况下适配；如需要改变骨架或目标尺寸，应先形成具体适配差异方案，当前不修改渲染代码。

每格只放对应的一个部件或第11格完整角色，不放编号、标尺、文字、水印、底色、画框和地面投影。引导线、锚点及编号只能放在源文件的隐藏技术图层或另交标注图上，不得烧进运行 PNG。

适配后的部件须统一已确认人物比例、服装结构、颜色、线条粗细、光照与视角，三阶段保留同一修士身份。现有六个主题ID是旧程序契约，三阶段与它们的文件映射尚未确定，不能据此自行扩写六套新人物。源画已确认统一为**右向四分之三视角、左上柔光**；具体造型由产品从候选审核确认。左向显示仍会镜像已画光影，固定世界光及非对称装饰的处理属于后续适配评审，不提前宣称已实现。

流程为：内置 GPT Image/imagegen 生成凡人 A1/A2/A3 候选与预览 → 产品审核、修改并选定身份 → 延展并确认同一人的三阶段 → Codex 单独制作游戏部件和资料，核对拆件、透明、锚点及现有骨架差异 → 接入并按本规范验收。候选须呈现完整全身及双脚，为动作和武器留空间，优先真透明，无字、水印、边框；凡人无灵气光环、华丽武器和高阶饰品。三张候选在同体系内的发型、脸、气质、剪影和配色须明显不同。生成使用内置工具，不切换 CLI；额外付费 API 必须先征得产品同意。

原始 AI PNG 是光栅输出，不能称作分层 PSD，也不能假定内置工具直接提供独立可编辑图层。分件、被遮挡连接区及可编辑源资料须在确认后另行制作。将来游戏资产的全身参考须由同一拆件母版拼装或严格回校，不能用本轮独立概念画代替已通过拼装的证明。

新图的 `.rects` 按表顺序写12行四整数，建议直接用完整格矩形；不得改成 `left,top,right,bottom`，不得写归一化比例，也不得把上述行列号当坐标。程序允许逗号、空格或制表符分隔，支持独立 `#` 注释行；不支持额外字段或尾随行内说明。交付以逗号分隔最易审计。

交付校验需要比当前解析器更严格：精确12条有效行、全部正尺寸、全部在PNG范围内、无重复或相交区域、顺序与部件名一致、PNG尺寸正确，并核对图集与rects版本/哈希。当前解析器只检查条数、正尺寸和越界，**不会证明顺序正确、区域不重叠或内容是对应部件**。

### 3.3 真实透明安全边与关节重叠

每格建议四边保留**至少32 px真实透明安全边**。令所有 alpha>0（包括半透明抗锯齿、光晕、头发和披风尾端）像素集合为 S；要求其包围盒满足 `minX≥32, minY≥32, maxX≤479, maxY≤479`。边带 `[0,31]`、`[480,511]` 的 alpha 必须全部为0。安全边不能只按 alpha>24 的运行裁切阈值测量，也不能用肉眼看到的主体边缘代替。

安全边的作用是保证格间隔离与后续导出余量；运行时的自动裁切会移除大部分安全边，**它不是最终角色在220×240窗口里的32 px留白**。最终窗口留白须单独测量。

11个部件分别保留完整形状和隐藏连接区，彼此不能在PNG同一格内粘连。肩、肘、胯、膝、踝及披风根的重叠应画在各自部件内部：例如上臂有圆润肩端与肘端，前臂有被上臂覆盖的肘帽，靴口包含被小腿覆盖的连接区。关节隐藏区建议在绑定后的220×240实际画面中保留**3–5 px实色重叠深度**，源图长度按该部件的实际缩放率反推；不得将固定32源像素直接等同于3–5显示像素。

头颈连接需要下颌/颈根与衣领形成可旋转重叠；领口不能只留空洞期待旧肤色补片永远正确。小腿与靴仍按当前“同一格、可分段重叠采样”的形状制作；若要改为独立脚掌图，是索引与渲染改造提案，不能自行挤占第11格。

需检查所有关节极限姿态：跑步收腿、双手握持、攻击前冲、喘气低头、死亡倾倒。不能用在身体上画第二只手、复制衣领或把披风直接烙进头部的方式掩盖断缝，这会随独立旋转暴露重影。

## 4. 锚点交付规范与后续数据驱动提案

### 4.1 候选锚点统一存原始 cell 坐标

新制作资料中的锚点统一存为**原始512×512 cell局部像素坐标 `cellPx`**，原点是该格左上角，浮点可用；不以自动裁切结果为原点，不以缓存图尺寸为原点。这样改透明余量或重新打包时，原始绘画与标注可以一起可追溯地移动。

每个点必须有语义名称与版本，技术标注须显示该点落在隐藏连接区或实际握柄中心。不能只交“pivot”一个点，因为单点不能确定肢体方向、长度和鞋底。最少点集为：

| 部件/对象 | 必交标注 | 绑定含义 |
|---|---|---|
| head | neckAttach；可选 faceCenter、eyeLine | neckAttach是下颌/颈根的连接中心，绑定torso.neck；face/eye只作可读性检查，不拉伸脸 |
| torso | neck、nearShoulder、farShoulder、nearHip、farHip | 身体各关节的目标连接点，需与服装的实际领口、袖口、裙下隐藏区一致 |
| 近/远上臂 | shoulder、elbow | 起点对肩，终点对肘；分别保留两端覆盖区 |
| 近/远前臂与手 | elbow、wrist、grip | elbow连接上臂；wrist标手腕；grip是手掌包住柄的中心，不能默认wrist=grip |
| 近/远大腿 | hip、knee | hip连接躯干，knee连接小腿 |
| 近/远小腿与靴 | knee、ankle、soleHeel、soleToe、footCutY | ankle为踝轴；sole两点定义支撑底线；footCutY定义组合图中的重叠采样起点 |
| cape | root；可选 restAxisEnd | root连接后肩/领后，restAxisEnd辅助记录静止垂落方向 |
| 武器 | mainGrip、supportGrip、twoHands | 两点位于武器原画实际柄上，主点绑近侧手grip，副点绑远侧手grip；单手武器明确关闭副点约束 |
| assembled-reference | 对齐基准线、颈/肩/胯/鞋底可视标注另交 | 用于校核拆件组合比例，不进入动作绘制 |

头部点绑定到躯干颈点，上臂在肩肘之间变换，前臂最终应以**grip**而非手腕绑定武器，手腕作为形状检查点。小腿绕膝踝变换，靴绕踝独立转动，支撑时soleHeel与soleToe等高。披风root随躯干，边缘允许摆动。这些是新数据模型的语义要求；当前源码仍只有Start/End/Ankle/Sole/FootCut和主题特判，尚不能直接消费这些额外字段。

### 4.2 自动裁切与锚点转换必须一起处理

令格在图集中的原点为 `C=(cx,cy)`；原始标注点为 `p_cell=(px,py)`；程序实际裁切矩形为 `B=(bx,by,bw,bh)`，坐标在整个图集上。则：

```text
p_atlas = C + p_cell
p_crop  = p_atlas - (bx, by)
        = p_cell - ((bx, by) - C)
```

若缓存最终尺寸是 `K=(kw,kh)`，则以**实际生成的缓存宽高**换算，不能仅使用未取整的理想scale：

```text
p_cache.x = p_crop.x * kw / bw
p_cache.y = p_crop.y * kh / bh
```

`kw/kh`受上限、`Ceiling`取整影响，两个比例可能有微小差异。原画锚点不随自动裁切隐式改变；调整部件在cell内的位置时必须同时移动其cellPx锚点。若未来选择在元数据直接存crop-local点，则须记录它所对应的确切B及裁切算法版本，每次改alpha轮廓都要重算；本文主规范不采用这种脆弱约定。

同样，当前头部归一化锚点和武器归一化双握点是相对于**裁切后的绘制框**，不能把原始512格比例直接塞入现有数组。后续适配层可从cellPx经过上述换算，再除以裁切/缓存尺寸得到所需归一化值。左右显示镜像应在装配后统一完成，不能把源锚点另行翻转一次，否则会双重镜像。

### 4.3 JSON仅为候选接口，不是现有能力

建议后续按主题新增 `rig-{theme}.anchors.json`，并为武器新增相应握点元数据。候选字段为：`schemaVersion`、`atlasFile`、`atlasSize`、`grid`、`coordinateSpace:"cellPx"`、`parts`、`rigTargets`、`neckConnector`、`weapons`。其中原画点与220×220基准的目标点必须用不同字段，禁止混用。

以下为格式示例，数值仅用于说明坐标系，**不是新角色已校准锚点**，不能直接用于生产：

```json
{
  "schemaVersion": 1,
  "status": "proposal-example-only",
  "atlasFile": "rig-OTHER.png",
  "atlasSize": [2048, 1536],
  "grid": { "columns": 4, "rows": 3, "cellSize": [512, 512] },
  "coordinateSpace": "cellPx",
  "parts": [
    {
      "index": 7,
      "name": "near-shin-boot",
      "cellOrigin": [1536, 512],
      "anchors": {
        "knee": [248, 88],
        "ankle": [252, 344],
        "soleHeel": [218, 432],
        "soleToe": [372, 432]
      },
      "footCutY": 304
    }
  ],
  "rigTargets": { "coordinateSpace": "rig220", "nearShoulder": [96, 112] },
  "neckConnector": { "mode": "pending-art-review", "color": null }

```

真正接入需另行实现：完整11部件/参考与武器字段校验、坐标转换、合法范围/零长度/可达性检查、明确错误信息、主题回退策略及版本兼容。对未带JSON的旧主题保留当前自动锚点与主题分支；如果提供JSON但内容损坏，应报告该文件和字段，不能静默丢弃后让美术以为标注已生效。是否允许逐部件回退需程序评审，不能由美术文件隐式决定。

在加载器、测试与验收更新之前，JSON只随候选资产资料交付，不进入当前运行包，不应在文案里写成“锚点已数据驱动”或“换图自动适配所有角色”。

## 6. 候选资产验收矩阵与可操作标准

以下是后续制作/接入阶段的验收门槛建议，本阶段只记录标准。技术自动化与人工小尺寸评审缺一不可；启动验证通过只说明基础载入条件满足。

### 6.1 文件与透明校验

| 检查项 | 方法与通过条件 |
|---|---|
| 尺寸/索引 | PNG精确2048×1536、RGBA；12条rects逐项匹配第3.2节；逐格预览与命名一致 |
| 真alpha | 透明背景像素alpha=0；12格都非空；有效alpha>24像素满足当前HasCell与1.5%门槛，整体透明率通过现有启动验证 |
| 源图安全边 | 对每格的所有alpha>0像素测包围盒，四边最小距离均≥32源像素；零散杂点和低alpha光晕也计入 |
| 无污染 | 每格分别合成到 `#151820` 与 `#F2F0E8`，100%与400%检查轮廓；不得有连续白边、黑边、矩形底或格间串色，半透明过渡颜色应来自该部件 |
| 元数据一致 | 记录PNG/rects/锚点哈希与版本；锚点处在正确连接区；裁切后转换点可在缓存图上复核 |

### 6.2 实际显示尺寸，不能只看大图

必须查看 **220×240（100%）**、**176×192（80%）**、**264×288（120%）** 三种实际输出，图片查看器固定100%像素显示，分别置于上述深/浅桌面底色。另保留220×220基准图以定位纵向拉伸差异，但不以它替代实际显示图。

验收样张应来自与运行相同的裁切、缓存和变换链。仅把2048图集缩成一张缩略图、只看第11格参考、或只看440/660大预览都不能证明最终清晰度。

- 面部：在176×192输出中，标出眼区、鼻口/面罩区、头部轮廓三个可辨识块。至少保留一个≥2显示像素宽的明确眼部暗/亮块，且眼区与相邻眉/帽沿之间至少有1显示像素的颜色或亮度分界；不能缩成不可区分的一团。封闭头盔方案可用清晰眼窗替代鼻口，但须产品批准。
- 表情/朝向：提供右向与镜像左向的同相位并排图，评审者在100%不放大时能指出视线与前进方向；不能只靠武器尖端判断方向。小脸细节无法成立时优先简化线条和强化色块，不增加源图纹理掩盖问题。
- 轮廓：头、躯干、手掌/武器、近远腿在小尺寸仍有可分离边界；关键装备不能只剩一条低alpha细线。远侧肢体可降低明度，但不能因alpha过低影响自动锚点或消失。
- 最终窗口边距：对角色本体、持有武器和随身披风组合的alpha>12包围盒测量。普通run/idle/pant/attack/dying各采样帧在220×240中四周至少留2显示像素；176×192至少1像素，264×288至少3像素。独立攻击特效、状态文字、光环须另记范围；复活的土层遮罩属于预期裁剪，应标注，不能拿它掩盖头/武器被窗口截断。仍需满足最外行列alpha≤12的既有测试。

### 6.3 动作、接缝、鞋底与握持

所有批准交付的主题均覆盖左右两个方向：run周期采样 `n/60，n=0…59`，另对比cycle=0与1无缝端点；idle/pant至少取0、0.25、0.5、0.75秒；attack取进度0、0.25、0.5、0.75、1；dying、grave、revive取阶段起点/中点/终点及切换邻近点。run/attack至少覆盖七种当前武器。慢放检查与原速观察都要做，静态漂亮的一帧不能代表整套合格。

| 部位 | 客观检查建议 |
|---|---|
| 头颈 | 颈点附近不得出现连接头与领的透明裂缝；最小尺寸中保持至少1显示像素的连续实色连接；在基准220图可沿用现有局部区域内alpha≥150的头/衣领重叠至少12像素检查，但新造型要重新确认区域和门槛，不只看补片覆盖 |
| 肩/肘/胯/膝 | 极限转角下仍有3–5显示像素设计重叠；不出现背景可见的裂缝、双手掌、双膝或袖口翻面；锚点标注与实际几何中心不应漂移 |
| 踝与鞋底 | 支撑时heel/toe底线等高；鞋底不穿过对应地面，镜像后仍平；靴子采样与小腿重叠处不露切边。记录支撑相连续帧的鞋底x变化，排查视觉滑步 |
| 主/副握持 | 将武器握点与手掌grip投影到最终输出：220×240下偏差≤2显示像素，176×192下≤2，264×288下≤3；手掌实色区域覆盖柄心，不能只是袖口碰到柄。boomerang按单手验收，副手不强拉 |
| 披风根 | 跟随后肩/领后连续，不与头部一起错误转动；摆动时根部不漂移，尾端不越窗口 |
| 左右镜像 | 近远层级、脚掌接触和双握点保持正确；非对称徽章、字样及强主光是否接受镜像由产品明示 |

### 6.4 现有验证可复用与必须调整处

- 保留 `HeroPoseRig.SelfTest` 的固定骨长、膝朝前、支撑足不滑、周期连续等约束；它检查数学骨架，不能单独证明新图的关节贴合。
- 保留 `AdventureRenderer.AssetsSelfTest` 的载入、透明、动作、双向边界、帧差异与GDI资源检查；补足当前多处220×220检查未覆盖的实际220×240与80%/120%输出。
- `HeadNeckPreview` 的颈点、局部±14窗口、alpha≥150重叠数假设与现有主题点绑定，新头型/领型/肤色需要更新；不能因旧测试过了就宣称新脸与颈部自然。
- `RigContactValidation` 在220×220里用y≥194、alpha>40判断脚底越界，且展示图使用191地面线；改尺寸后要按W/H缩放相应检测线，保留近侧191/远侧188区别。新靴型也要复核自动鞋底检测。
- 部分素材特征测试按既有颜色/固定区域寻找眼睛等像素（例如 `AdventureArt.cs` 的怪物眼睛颜色和行段）；若后续同时重制这些素材，应更新成新资产可复核的特征或标注，不能要求新画沿用旧配色只为让旧断言通过。
- `AtlasInspect` 通过alpha连通域估计部件并可能写rects，不能替代新规范的固定格与人工语义核对；有多个不相连饰件时，连通域数量不等于部件数量。后续若使用，应在候选目录运行并审查输出。
