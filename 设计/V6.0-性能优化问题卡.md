# 《桌面修仙传》V6.0｜性能优化问题卡（CPU 分模块测量）

测量日期：2026-10-17 ｜ 测量代码：feature/v6-dongtian @ 基于 5f599f3（PR #4 最终整改）＋ `--perf-probe` 探针
测量工具：`源代码/PerfProbe.cs` + `骑士助手.exe --perf-probe <分钟>`（默认 3 分钟，已并入本分支，可随时复测）

## 一、测量方法（如实说明）

- 隐藏宿主窗体 + 演示控制器（不写真实档案、不触网络），合成忙碌战场：3 文件怪 + 5 虚拟妖物（每 5 秒补足）+ 内存 Boss + 磁盘 Boss，自动作战开启，炼气 6 层战力系数。
- 按 15ms 节拍驱动主 Tick（与生产定时器同节奏），逐段秒表计时：修炼/百业/清理回收/磁盘/连通性/战斗核心/战斗移动/敌循环/世界维护/存档/渲染（含 render.hero、render.enemies、render.windows 子项）。
- 演示模式跳过 cultivation/baiye 结算（表中近零）；生产模式这两块为周期性轻量运算，不改变结论。
- 测量期间本机同时运行 PR #1 长测程序（约 2 核负载），属真实并存场景；数据为 2 分钟稳态采样。

## 二、分模块数据（120.1s 墙钟 / 进程 CPU 62.9s ≈ 52.4% 单核，整机 12 核 ≈ 4.4%）

| 模块 | 总耗时 | 占整拍比例 | 每拍均耗 | 结论 |
|---|---|---|---|---|
| tick-total | 67.7 s | 100%（56% 单核） | 29.0 ms | 每拍超时：15ms 节拍实际只能跑到 ~19.5 拍/秒 |
| render.enemies | 40.0 s | **59.1%** | 17.1 ms | 妖物精灵 GDI 重绘，每拍 4 只切片，单只 ≈4.3ms |
| render.hero | 21.7 s | **32.0%** | 9.3 ms | 主角每拍全量重绘（66fps 意图） |
| combat-move | 3.1 s | 4.6% | 1.3 ms | PlanNext/战术/移动每拍执行 |
| render（余量） | 2.7 s | 4.0% | 0.6 ms | 地标/窗口管理/HeroVisual 构造等 |
| render.windows | 0.3 s | 0.4% | 0.07 ms | 窗口增删与 LINQ 分配 |
| enemy-loop / world-maint / battle-core / connectivity / cultivation / cleanup / save / baiye / disk | 合计 <0.1 s | <0.2% | <0.01 ms | 逻辑与结算近乎免费 |

**核心结论：CPU 消耗的 ~95% 在渲染管线（精灵逐拍重绘），战斗逻辑、修炼结算、存档、磁盘/内存/网络采样合计不到 5%。**

与 PR #1 长测（139 分钟，稳定 ~200% 即 2 核）的关系：长测为生产模式 + 真实演员数（最多 11）+ 真实磁盘/内存/连通性采样 + 实际屏幕呈现，绝对值高于本探针；模块占比结论一致指向渲染主导。优化落地后应以 `--perf-probe` 复测并期待 tick-total 成比例下降。

## 三、优化计划（按预期收益排序；均为局部改造，不重写系统）

> **2026-10-17 更新：P0、P1 已落地并完成前后对照实测，实测数据见 [V6.0-性能优化第一轮实测报告](V6.0-性能优化第一轮实测报告.md)。** 忙碌战场实测 CPU −13%、整拍 −26%（最差场景，未达预期上限）；静止场景实测降至 10.6% 单核。P2 优先级下调（combat-move 已仅占 4–5%），P3 本轮跳过。

- **P0 动画帧量化 + 脏标记跳绘**（预期 −60~80% 渲染耗时）：主角/妖物动画时间量化到 ~12fps 帧序号，（帧、相位、朝向、血量档位、标签）任一不变则跳过 PaintWindow，仅更新窗口位置。妖物 idle 且非脏完全跳绘。
- **P1 自适应节拍**（预期空闲时 −50% 整拍）：无战斗动画、无拖拽、无新事件时定时器 15ms → 33ms（30fps 足够桌宠流畅），战斗/演示期间恢复 15ms。隐藏桌宠已走 enabled=false 早退（现为零渲染），保持不变。
- **P2 索敌降频**（预期 −3~4%）：PlanNext 与战术规划从每拍改为 5Hz 或目标/冷却/授权集合变化时再算。
- **P3 渲染分配修整**（预期 <1%，顺手）：RemoveUnusedWindows 的 HashSet/LINQ 每拍分配改复用缓冲；地标 4Hz 已有限流保持。
- **暂不进行**：渲染后端替换（Direct2D/Skia）、精灵图集预烘焙——属大规模重写，待 P0–P2 落地复测后再评估必要性。

## 四、验证要求

每项优化落地必须：① `--selftest` 与 `--adventure-smoke` 全绿；② `--perf-probe` 同场景复测附前后对比；③ 确认动画观感无跳帧投诉（帧量化不低于 10fps）。

## 五、风险

- 帧量化若按 wall-clock 取帧，暂停/恢复后相位可能跳变——用累计 renderTime 取帧规避。
- 降频索敌在怪物贴脸时反应变慢——保留"新授权/新受伤立即重算"的触发。
